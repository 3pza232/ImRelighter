# 04 · 渲染与着色器设计

## 目标

在 Android 上复现桌面端“深度 → 法线 → 重打光”的核心视觉能力，同时接受移动 GPU 在精度、带宽、发热和屏幕尺寸上的约束。

MVP 渲染目标：

- 原图、深度、法线、灯光结果四种视图；
- 法线/深度结果可用于照明；
- 单图导出 PNG；
- GLES 3.1 为最低基线，优先利用 3.2 能力；
- 不依赖桌面 OpenGL 4.5 专属接口。

## 图形栈

| 项 | 决策 |
|---|---|
| API | OpenGL ES 3.1 最低，3.2 优先 |
| 窗口/表面 | Kotlin `SurfaceView` + native EGL |
| UI | Dear ImGui 1.92.5 + `imgui_impl_opengl3`（ES3 模式） |
| 着色器 | GLSL ES 3.10/3.20，按能力编译变体 |
| 坐标 | 统一规定纹理/深度为 top-down，FBO 显示时显式翻转 V |
| 颜色 | 线性光照，sRGB/tonemap 在最终 pass 处理 |

不使用桌面 `glGetTexImage`、计算着色器、桌面 GL 4.5 特性。导出通过 FBO + `glReadPixels`。

## 渲染 Pass

建议的每帧/每次文档更新流程：

1. **源纹理上传**：原图 RGBA8，mipmap 可选。
2. **深度上传**：归一化深度优先 `GL_R32F`，不可用时回退 `GL_RG16F`/`RGBA16F` 或 RGBA8。
3. **深度平滑（可选）**：对应桌面 `depth_smooth.frag`，用于高平滑档；移动端先关闭以降低复杂度。
4. **法线生成**：对应 `normal.frag` 的算法；见下文移动端变体。
5. **阴影贴图**：每盏启用阴影的灯一个深度目标；MVP 限制灯数和分辨率。
6. **光照**：对应 `lighting.frag` 的 PBR/聚光/材质路径。
7. **合成/tonemap**：输出到默认 framebuffer。
8. **ImGui**：最后绘制 UI，避免 UI 被 tonemap 影响。

所有 pass 的资源由 native `Renderer` 持有；Kotlin 不直接持有 GL 对象。

## 法线生成的移动端结论

已完成的真机验证（V2243A / Adreno 740）：

- q4f16 模型在 arm64 上产生高频深度噪声，法线轮廓出现密集点状噪点；
- q4 模型（4-bit 权重、FP32 激活）在该设备上干净；
- 深度先做 5×5 中值滤波；
- 法线在 **模型深度分辨率 518×714** 上计算，再放大到显示分辨率；
- 法线纹理生成 mipmap 后显示；
- CPU 法线路径作为稳定基线，GPU `normal.frag` 移植保留用于诊断/后续优化。

正式渲染器建议：

- 默认使用 q4 深度；
- 法线计算优先在深度分辨率完成，避免对双线性放大的深度做全分辨率中心差分；
- GPU 法线若启用，必须用真机 golden image 验证轮廓；
- 不把 RGBA16F 法线目标作为硬要求；RGBA8 在 Adreno 上已验证可用；
- 保留 CPU 法线回退，防止特定 GPU 的采样/精度差异导致不可用。

## 精度与格式

- 深度：`GL_R32F` 为理想格式；必须检测 FBO/纹理能力并准备回退。
- 法线：RGBA8 足够用于显示和照明；编码为 `n*0.5+0.5`。
- 阴影：深度纹理优先 `GL_DEPTH_COMPONENT24`/`GL_DEPTH_COMPONENT32F`，按设备能力选择。
- 颜色：中间目标优先 RGBA8；需要 HDR 时使用 `RGBA16F`，但必须有扩展检测。
- 所有浮点纹理/FBO 在初始化时检查 `glCheckFramebufferStatus` 和 `glGetError`，失败则降级并记录。

## 阴影与灯光

桌面端有 8 灯、阴影贴图和多 pass。Android MVP 不直接照搬：

- MVP 建议 4 盏灯，默认 1–2 盏启用阴影；
- 阴影贴图 1024×1024 起步，按设备能力和帧率调整；
- 使用简单 PCF（3×3）而不是高成本大核模糊；
- 灯光数量、阴影开关、阴影分辨率作为质量档位；
- 先保证单灯/双灯正确，再扩展到 4 灯；
- 8 灯和复杂软阴影作为后续增强，不作为 MVP 验收条件。

## 导出

- 使用离屏 FBO 渲染到目标尺寸；
- `glReadPixels` 读取 RGBA8，按需要垂直翻转；
- PNG 编码复用桌面端导出算法/实现（移植到 native）；
- 大图分块读取，避免一次性峰值内存；
- 导出线程不得直接使用 UI 线程的 GL 上下文；由 GL 线程执行 GPU 读回，编码可交给工作线程。

## 资源与生命周期

- EGL context 丢失时销毁并重建所有 GL 资源；
- 文档切换/推理完成后只更新受影响纹理，不重建整个 renderer；
- 纹理、FBO、shader program 采用 RAII 包装，禁止裸 `glDelete*` 散落；
- 每个 pass 有明确输入/输出尺寸，禁止隐式使用 viewport；
- 所有 shader 编译/链接失败必须显示可读错误，而不是黑屏。

## 性能预算

- 目标：编辑预览 30 FPS（中端 arm64）；
- 推理是异步任务，不阻塞 UI；
- 法线/阴影只在文档或参数变化时重算，不每帧重算；
- 监控：GPU 帧时间、纹理内存、推理耗时、导出峰值；
- 发热/降频时允许自动降低阴影分辨率或关闭阴影。

## 验收标准

- GLES 3.1 设备可启动并显示原图；
- q4 深度在 arm64 真机上无 q4f16 式轮廓噪点；
- 法线/深度方向与桌面一致；
- 单灯、双灯、阴影开关结果正确；
- 导出 PNG 与预览方向/颜色一致；
- 无 GL 错误、无 FBO incomplete、无纹理泄漏；
- 真机截图进入 golden 测试基线。
